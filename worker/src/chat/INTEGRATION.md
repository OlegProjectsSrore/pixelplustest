# Подключение классификатора чата

Проверено 2026-10-22, повторно после реализации и испытания `handler.ts` и подключения общего `channel-runtime.ts`. Этот документ описывает реализованный адаптер и необходимые действия владельца ядра. Ядро, схемы хранения и библиотека изменяются параллельно; приведённые ниже наблюдения относятся к прочитанным версиям функций, а не объявляют интеграцию завершённой.

## Реализованные экспорты

| Модуль | Экспорт | Назначение |
| --- | --- | --- |
| `classifier.ts` | `classifyTurn(context, runtime)` | Ровно одна разрешённая попытка DeepSeek; возвращает `ClassificationResult`. Не записывает состояние и не повторяет запрос. |
| `classifier.ts`, `prompt.ts` | `buildClassifierPrompt(context)` | Формирует инструкции и отдельное JSON-сообщение с данными. Не включает текст рекомендаций, PDF или шуток. |
| `classifier.ts`, `validation.ts` | `parseClassification(payload, context)` | Проверяет структуру, типы, словарь, ссылки, цитаты, исправления и совместимость намерения с фактами/юмором. При нарушении бросает `ClassificationValidationError` без исходного текста в сообщении. |
| `build-context.ts` | `buildChatContext(input)` | Строит контекст из закреплённой `AuditLibrary`. Проверяет утверждение каждого вопроса и факта. `allowDraft` по умолчанию `false`. |
| `build-context.ts` | `buildClassifierContext(lib, state, events, existingAnswers, currentQuestion, mode, sourceEvents)` | Краткая обёртка с утверждённой библиотекой; для пилота с черновиками использовать явный `buildChatContext({allowDraft:true,...})`. |
| `handler.ts` | `createChatHandler(dependencies)` | Создаёт `AdapterHandler` для `ChannelAdapters.chat`; проверяет доступ и состояние, обрабатывает выбор/текст, передаёт один подготовленный ход в атомарную функцию ядра. |
| `handler.ts` | `selectionAnswers(input, question, lib, event, now)` | Сопоставляет выбор с текущими вариантами без LLM. Для `context_priority` разрешает несколько разных тем; для остальных вопросов — один вариант. |
| `types.ts` | Типы адаптера | `ClassifierContext`, `AnswerCandidate`, `Classification`, `ClassifierRuntime`, `ProviderExchange`, `ValueSchema`. Общие типы импортируются из `audit/contracts.ts` и `audit/library.ts`. |

В `ChatContextInput` обязательны `lib`, `state`, `events`, `existingAnswers`, `currentQuestion`, `sourceEvents`; `mode` по умолчанию `chat`. Дополнительно доступны `allowedQuestionIds`, `faqs`, `clarificationQuestions`, `allowedAttemptIds`, `allowDraft`.

Без `allowedQuestionIds` передаются текущий вопрос, доступные вопросы фазы `orientation` и ранее отвеченные вопросы этой версии. Остальные факты модель не может возвращать: ядро расширяет разрешённый набор явно. История ограничена последними 12 текстовыми событиями; исходные события для новых свидетельств передаются отдельно и не подменяются этой историей.

## Зависимости createChatHandler

`createChatHandler({runtime, commitTurn, context?})` требует обе функции `runtime` и `commitTurn` уже при создании. Нет запасного варианта с последовательными частичными сохранениями через `core.accept`, `core.humor` и `core.finish`.

**Подключение уже реализовано:** `channel-runtime.ts` предоставляет `createChatRuntime`, `commitChatTurn` и `createChatAdapter`; `integration.ts` устанавливает `channelAdapters.chat = createChatAdapter()`. Их сигнатуры совместимы с обработчиком. Это действующие зависимости, не отсутствующие hooks. Общий модуль подключения создан владельцем ядра и в данной задаче проверен только чтением.

- `runtime(adapterContext, authenticatedSession, operationId, attempt)` возвращает `ClassifierRuntime`. `attempt` равен 0 или 1. Резервирование и сохранение исхода выполняются предоставленным ядром `runAuthorized`; создание runtime само по себе не должно запускать внешний запрос. Доверенная сессия — отдельный аргумент `authenticatedSession`, а не присланное/закешированное поле `adapterContext.session`.
- `commitTurn(request, adapterContext, authenticatedSession, preparedTurn)` — обязательная атомарная зависимость. `preparedTurn` содержит `input`, `request_hash`, исходное `event`, `answers`, полную `classification` либо `null` для стандартного выбора, `action` и `service_text`. Ядро в одной согласованной операции проверяет текущие ревизии/канал/время, валидирует ответы, применяет паузу/возобновление/завершение и предпочтение юмора, выбирает готовую служебную реплику, сохраняет ответ операции. Ошибка зависимости передаётся вызывающему коду; обработчик не выполняет скрытого частичного commit.
- `context(adapterContext, authenticatedSession, lib)` опционально предоставляет разрешённые ID вопросов/попыток, утверждённые FAQ `{id,question,answer}` и уточнения `{id,text}`. Клиент не может передать эти каталоги в теле запроса. Текст служебного ответа выбирается из этого каталога или из фиксированного безопасного уточнения обработчика, а не генерируется моделью.

До провайдера обработчик сам вызывает `core.authenticate`, проверяет хеш и сохранённый исход операции, ревизии, версию, текущий вопрос, канал, статус и время. После медленной подготовки контекста/runtime время проверяется снова; тайм-аут ограничивается остатком времени опроса. Повтор принятой операции с тем же телом возвращается до проверки текущего вопроса/ревизии; изменённое тело получает конфликт без нового расхода.

Повтор классификации организован в обработчике: только `provider_output + retryable` разрешает попытку 1. Перед ней повторно проверяются аутентификация, сохранённый результат, ревизии, состояние и время. Сетевые ошибки, HTTP-ошибки провайдера и тайм-аут не повторяются. После двух невалидных результатов сохраняется служебное уточнение с пустым `answers`. `content_filter` также даёт безопасное уточнение без повторной попытки.

`mixed` передаёт факты и выбранный FAQ в одном `commitTurn`; юмор запрещён. `pause`, `resume`, `finish` передаются как действия без выдуманного ответа или самостоятельного следующего вопроса. В паузе обработчик допускает только `resume` и `finish`. `decline` с проверенными кандидатами сохраняет именно их; один `intent:"decline"` с пустым `answers` не создаёт `declined` для каждого факта вопроса, а вызывает уточнение. Предпочтение юмора остаётся в `classification` и применяется ядром вместе с остальным ходом.

## Результат и преобразование в AuditAnswer

Результат содержит только `intent`, `answers`, `clarification_question_id`, `faq_id`, `joke_category_id`, `humor_preference`. Свободного текста ответа посетителю нет. FAQ и уточнения выбираются только из явно переданных ядром ID. Категория шутки является предложением для общего обработчика.

`AnswerCandidate` содержит `question_id`, `fact_id`, `state`, `value`, `event_ids`, `evidence: [{event_id,text}]`; опциональны `answer_id`, `parameters`, `replaces_answer_id`. Опциональное поле отсутствует, а не заменяется `null`. Допустимые состояния: `known`, `unknown`, `not_measured`, `not_applicable`, `declined`, `ambiguous`, `other`. `not_asked` и `conflicting` вычисляет ядро.

Обёртка перед сохранением:

1. Проверяет ревизии, закреплённую версию, активность канала, паузу, срок сессии и остаток времени; получает исходные события с сервера.
2. Проверяет сохранённый результат `operation_id` и хеш тела до классификации. Повтор принятой операции возвращает прежний результат.
3. Для кнопочного выбора не вызывает LLM; сверяет вариант с текущим вопросом.
4. Для текста получает кандидатов, сохраняет их исходные свидетельства и удаляет дополнительное поле `evidence` из объекта, передаваемого `validateAnswers`. Ядро сохраняет ссылки `event_ids`; дополнительные пользовательские поля не копируются в `AuditAnswer`.
5. Назначает `id`, `channel`, `method`, `confirmation`, `library_version`, `created_at`. Кандидаты LLM покидают обработчик как `unconfirmed`. Текущий `commitChatTurn` после проверок словаря и исходного письменного сообщения применяет политику ядра: явные письменные сведения получают `explicit`. Это подтверждение сообщения посетителя, а не независимая проверка достоверности бизнеса; состояния `ambiguous` и вычисленные противоречия сохраняют ограничения.
6. Явное исправление адресует активный ответ того же факта. Ядру также нужно событие `kind: "correction"`; обычное противоречие не превращается в исправление. Старое значение остаётся в истории.
7. Передаёт кандидатов в общее атомарное изменение. Следующий вопрос выбирает ядро после принятия данных. Сам адаптер не объединяет ответы, объекты или массивы.

ID `target` и `alternative` повторяются между фактами. Проверяется тройка `answer_id + question_id + fact_id`, а не глобальная уникальность `answer_id`. `buildChatContext` использует `fact.values[].id`, учитывает `meaning`, `entailment`, `training_paraphrases`, `bare_yes_no`, пограничный и отрицательный примеры разрешённой группы из `answer-options`.

При `mixed` сохраняются проверенные содержательные ответы; юмор запрещён. При `off_topic`, `sensitive`, `pause`, `finish` и других служебных намерениях кандидаты фактов запрещены. Для просьбы паузы/завершения нужно действие ядра без следующего вопроса. Одновременные факты и управление разговором требуют отдельного согласованного решения в обёртке: одно поле `intent` не кодирует одновременно `mixed` и `pause`.

Цитата проверяет происхождение, но сама по себе не доказывает правильность смысловой нормализации. Семантика исправления, полнота извлечения и отсутствие ложной уверенности требуют независимой проверки на диалогах. Прохождение модульных тестов не подтверждает цель 95%.

## Внешний вызов и резерв расходов

`ClassifierRuntime` требует `api_key`, `max_tokens`, `timeout_ms`, `runAuthorized(request, call)`; `fetch` можно передать из `core.fetcher`. Прямого чтения `Env` в адаптере нет.

`request` содержит `provider: "deepseek"`, `model: "deepseek-flash"`, `max_tokens`, `input_utf8_bytes`. Последнее поле — размер входа в UTF-8, а не измеренный расход токенов; ядро задаёт консервативный резерв с учётом выбранной единицы бюджета и накладных расходов. API-ключ в метаданных резервирования отсутствует.

Обязательный контракт `runAuthorized`:

1. Создать устойчивый ключ попытки из сессии, операции и номера попытки; повтор доставки не создаёт новую попытку. Привязать операцию к неизменному телу запроса.
2. Атомарно получить право на расход. Наличие старой записи `reserved` не даёт права запускать провайдера повторно. Для текущего хранилища признак победителя — `newlyCreated === true`.
3. После разрешения вызвать `call()` не более одного раза. В callback входят запрос, ожидание и полное чтение ответа. Завершение HTTP-заголовков ещё не означает завершение расхода.
4. Принять `ProviderExchange`. При `usage !== null` учесть фактические токены даже при невалидной классификации; при `usage === null`/`outcome: "unknown"` сохранить неопределённый резерв, не списывать ноль.
5. Сохранить исход операции так, чтобы сетевой повтор после ответа провайдера, но до принятия фактов не запускал оплачиваемый запрос заново. Если результат потерян, возвращать штатную неопределённость/уточнение, а не скрытый повтор.

Внутренняя защита callback от двойного вызова действует только в одном экземпляре `classifyTurn`. Между разными HTTP-запросами необходима защита D1. Обработчик допускает один ограниченный повтор невалидного результата; ядро выдаёт для него отдельный резерв с устойчивым номером попытки. Максимум две попытки на логическую классификацию.

`ProviderExchange.outcome` равен `completed`, `http_error` или `unknown`. Даже у `completed` возможен `usage:null`. Адаптер не считает неизвестный расход бесплатным и не пересылает тело ошибки провайдера посетителю. Тайм-аут действует на запрос и чтение тела; отмена соединения не доказывает отмену вычислений у провайдера.

## Настройки

| Настройка | Текущее состояние |
| --- | --- |
| `runtime.api_key` | `createChatRuntime` читает серверный секрет `env.DEEPSEEK_API_KEY`. `Env` допускает его через индексную сигнатуру; runtime проверяет строковый тип. В браузер не передавать. |
| `runtime.max_tokens` | Обязательное целое от 1 до 16384; ограничение адаптера. Текущий общий runtime задаёт 4096. Это конфигурация, не измеренный показатель качества интервью. |
| `runtime.timeout_ms` | Обязательное конечное число от 1 до 60000. Общий runtime задаёт 12000; обработчик дополнительно ограничивает остатком времени опроса. |
| `BUDGETS_JSON` | `createChatRuntime` требует положительные `deepseek_calls`, `deepseek_tokens`, `deepseek_usd_micros`. До запроса резервирует 1 вызов, `input_utf8_bytes + max_tokens + 256` токенов и верхнюю стоимость по пиковым ставкам из `src/deepseek-cost.ts`. После ответа учитывает usage и стоимость ввода/вывода с проверенным кешем; отсутствие usage сохраняет оба неопределённых резерва. |
| `ALLOW_DRAFT_LIBRARY` | Существующий флаг ядра. Обёртка передаёт `core.engineOptions.allowDraft`; адаптер самостоятельно не разрешает черновики. |

Провайдерские поля фиксированы: `deepseek-flash`, `thinking: {type:"disabled"}`, `response_format: {type:"json_object"}`, `stream:false`, `temperature:0`. JSON Schema провайдеру не отправляется. Требование JSON и пример включены в инструкции. Принимается только `finish_reason:"stop"` и прошедший локальную проверку результат. Официальные источники: [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/), [JSON Output](https://api-docs.deepseek.com/guides/json_mode/), [ошибки](https://api-docs.deepseek.com/quick_start/error_codes/), [ожидание ответа](https://api-docs.deepseek.com/quick_start/rate_limit/).

## Подтверждённые границы интеграции на момент проверки

1. **Владение резервом — исправлено владельцем ядра и перепроверено.** `CoreServices.reserve` теперь требует одновременно `state === "reserved"` и `newlyCreated === true`. `D1Store.reserveUsage` возвращает `newlyCreated:false` для повторного ключа. Прежнее замечание о двойном запуске через этот метод больше не является текущим блокером. `runAuthorized` должен использовать этот путь, а не считать любую старую запись `reserved` новым разрешением.
2. **Хеш служебной операции — исправлено владельцем ядра и перепроверено.** `CoreServices.humor` и `acknowledgeHumor` теперь передают `requestHash: digest` в `store.commit`. Хеш также передаётся в обычные ответы, завершение и смену канала. Обработчик чата самостоятельно проверяет хеш при replay до внешнего вызова и передаёт его обязательному `commitTurn`.
3. **Частичная история.** `validateHistory` требует восемь полей попытки; `deriveFacts` сравнивает целые значения вместо слияния независимых полей. Дополнительный ответ по той же попытке может стать конфликтом. `needsQuestion` ищет незаполненные поля со `state:"not_asked"`, но `validateHistory` использует список допустимых состояний, в котором `not_asked` отсутствует. Нужен отдельный серверный сборщик истории по `attempt_id` и различение незаданных полей от неизвестных со слов посетителя. Нельзя выдавать пустые поля за неизвестность ради прохождения валидации.
4. **Политика подтверждения определена общим модулем подключения.** `handler.ts` передаёт результат LLM как `unconfirmed`, а `commitChatTurn` после core-валидации делает письменные сведения `explicit` в смысле «явно сообщил посетитель». Это соответствует различию письменного ответа и отдельного пересказа ключевых голосовых фактов. Обязательное повторное подтверждение каждой письменной фразы не является незавершённым требованием. `ambiguous` не становится `known`, противоречащие известные значения остаются `conflicting`; они не получают доказательный вывод только из-за `confirmation:explicit`. Тест обработчика с заглушкой commit показывает состояние до этой политики; он не описывает финальное состояние реального `commitChatTurn`.
5. **Схемы реальной библиотеки.** При проверке `context.model.values` был массивом строк, хотя `FactDefinition`/`validateAnswers` ожидают `{id,label}`. Многие объекты содержат `example_schema` или описания полей человеческим языком; `context.budget` не содержит явной схемы структурного значения. `buildChatContext` для таких фактов исключает `known` и сохраняет содержательные слова как `other`; это честное ограничение пилота, не полноценная типизированная история/бюджет. При появлении утверждённых типов можно расширить проекцию; конструировать их по догадке адаптер не должен.
6. **Восстановление оплаченной попытки до commit остаётся ограниченным.** `createChatRuntime` сохраняет расход через `settleUsage`, но не сохраняет `ProviderExchange`/классификацию/подготовленный ход. Если провайдер ответил, а `commitChatTurn` не произошёл (сбой процесса или конфликт ревизии), `getOperation` не содержит результата. Повтор того же `operation_id` встречает уже существующий резерв попытки 0 и получает конфликт; восстановить полученный результат из D1 нельзя. Второго расхода нет, однако прежняя операция застревает. Нужен устойчивый исход попытки/операции для воспроизведения либо сохранённый штатный исход ошибки/уточнения; нельзя обходить это скрытым новым запросом. Такой же ключ остаётся занят, если резерв calls был освобождён после отказа резервирования tokens ещё до fetch. Общий модуль подключения здесь не изменялся.

Общие файлы по этим замечаниям адаптером не изменялись. Перед применением сверить функции заново: владельцы ядра и библиотеки работают параллельно.
