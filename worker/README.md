# Сервер предварительного аудита

Серверные контракты находятся в `src/audit/contracts.ts`, HTTP-обработчики — в `src/index.ts`, интерфейс подключаемых каналов — в `src/integration.ts`. Все временные значения в контрактах и D1 — миллисекунды Unix. Библиотека закрепляется по версии; неизвестная версия не заменяется текущей.

## OpenAI Realtime, 26 октября 2026

Новые голосовые соединения используют `gpt-realtime-2.1` (с 26 октября 2026 вместо `gpt-realtime-2.1-mini`, которая путала фразы и проговаривала служебные указания), голос `ash`, скорость `1.0`. Постоянный ключ хранится только в секрете Worker `OPENAI_API_KEY`. Модель задаётся в `OPENAI_REALTIME_MODEL`; промпт и инструменты у обеих моделей одинаковые. Русские субтитры входящей речи формирует `OPENAI_TRANSCRIPTION_MODEL=gpt-live-transcribe`. Текстовый канал и восстановление фактов продолжают использовать существующий DeepSeek.

`dist/assets/audit-realtime.js` использует встроенный WebRTC браузера. Клиент передаёт SDP offer в авторизованный `POST /api/voice/start`; Worker резервирует действующие бюджеты, вызывает OpenAI `POST /v1/realtime/calls` и возвращает SDP answer. Повтор операции возвращает тот же зашифрованный в D1 ответ, без нового платного вызова. `POST /api/voice/control` принимает `{session_id, call_id, action: "heartbeat" | "stop", delivery_complete?}` с management token; heartbeat не изменяет ревизию опроса. Stop идемпотентен и применим только к принадлежащему сессии звонку. Функции опроса используют прежние серверные проверки цитат, фактов и права на канал. Новый вопрос и инструкции возвращаются после сохранения ответа. Реплики обеих сторон выводятся по событиям Realtime и сохраняются с ревизиями; при переключении ещё не извлечённые окончательные ответы восстанавливаются существующим классификатором.

Переключение в чат немедленно освобождает микрофон/воспроизведение, доставляет накопленные реплики и вызывает серверный hangup. Таймер останавливается после подтверждения сервера. Клиент отправляет heartbeat каждые 15 секунд. Cron останавливает соединения без heartbeat более 60 секунд и соединения с исчерпанным временем; при закрытии вкладки или потере сети возможна задержка до следующего минутного запуска Cron. Неподтверждённая остановка блокирует новый звонок. Если ответ на создание потерян вместе с provider call ID, резерв сохраняется до максимального срока Realtime-сессии (60 минут плюс 30 секунд), поскольку безопасно повторить создание нельзя. Это ограничение восстановления, а не автоматический повтор платного вызова.

Миграция `0006_realtime_calls.sql` добавляет состояние heartbeat и доставки, сохраняя существующие таблицы владения звонками и старые записи Ultravox. Старый адаптер оставлен для сверки ранее созданных звонков; новые звонки и обновление квот Ultravox отключены. Прежние суточные бюджеты не увеличены; для отладки OpenAI допускается один одновременный звонок. Лимит двух переподключений старого провайдера не применяется к OpenAI, но все старты по-прежнему проходят суточный бюджет `voice_starts`.

Проверки: `worker/test/channel-realtime.test.ts`, `worker/test/realtime-runtime.test.mjs`, `dist/assets/audit-realtime.test.mjs` входят в `npm test`. Дополнительно `node ../scripts/test-realtime-panel.mjs` из папки Worker проверяет настоящий клиент, представление и новый адаптер в браузере с подменёнными WebRTC и HTTP. Эти тесты не являются проверкой слышимого качества речи. Старые разделы о публикациях ниже описывают состояние на указанные даты.

Документация API: [WebRTC](https://developers.openai.com/api/docs/guides/voice-webrtc?voice-api=realtime), [события клиента](https://developers.openai.com/api/reference/resources/realtime/client-events), [завершение звонка](https://developers.openai.com/api/reference/resources/realtime/subresources/calls/methods/hangup), [модель Mini](https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini).

## Проверка и сборка

Из папки `worker`:

```powershell
npm ci
npm run typecheck
npm test
npm run check:library
npm run build:sdk
npm run build
npm run smoke
```

`build` выполняет только локальную сборку Wrangler (`deploy --dry-run`). Он не публикует Worker. Проверка выпуска с утверждённой библиотекой:

```powershell
node --experimental-strip-types ../scripts/build-audit-assets.mjs --production --check
```

Без `--check` сборщик сохраняет манифест точных входных байтов, компактные голосовые блоки и статистику в `.artifacts/audit-assets` корня проекта. Исходные JSON не переписываются. Без `--production` допускается техническая проверка черновиков. Черновые правила и тарифы не включаются в рекомендации даже в режиме разработки.

Схемы редакторских примеров из `src/audit/data` проверяются отдельно от сохранённого состояния Worker. `src/audit/runtime-schemas.ts` описывает реальные `AuditState`/`AuditResult`; сборщик проверяет по ним начальное состояние и результат анализа, затем выпускает `worker-state.schema.json` и `worker-result.schema.json`. Связи с библиотекой, доказательства, граф действий и утверждение дополнительно проверяет `validation.ts`.

`value-schemas.ts` задаёт формальные структуры сумм, периодов, деталей, влияния и прошлых работ по полям исходной библиотеки. Частичные значения не дополняются предположениями; совместимые поля объединяются, попытки работ различаются по `attempt_id`, противоречия остаются открытыми. Неописанный словарь, например строковые значения `context.model` без ID, сохраняется как `other` до уточнения библиотеки.

Тесты D1 выполняют SQL миграции на настоящей SQLite (`node:sqlite`), включая конкуренцию ревизий, аренды, повторные операции и откат транзакции. Это локальная проверка логики, а не измерение CPU и квот Cloudflare.

`npm test` запускает тесты Node для Worker, каналов, клиента и схем. Отдельный `npm run test:browser` запускает `dist/assets/audit-browser.test.mjs`: ему нужен установленный Playwright (при необходимости `PIXELPLUS_PLAYWRIGHT_MODULE` — file URL его модуля) и браузер. По умолчанию используется канал `msedge`; другой установленный канал задаётся через `PIXELPLUS_BROWSER_CHANNEL`. Браузерный тест подменяет HTTP провайдеров и не проверяет живой WebRTC.

`smoke` запускает собранный Worker в настоящем workerd через установленный Miniflare, применяет все миграции к локальной D1 и проверяет HTTP, права доступа и конкурирующие изменения. Внешняя сеть в этом тесте запрещена. Сквозной `client-worker.test.ts` использует настоящий клиент, HTTP transport и Worker; подменены только представление DOM и ответы внешних провайдеров.

`build:sdk` создаёт `dist/assets/ultravox-sdk.js` относительно корня проекта: автономный ESM с экспортом `UltravoxSession`. Зафиксирован `ultravox-client@0.6.0`; его допустимая зависимость `livekit-client` закреплена на `2.20.1`, совместимой с локальной сборкой на Node 22.18. Более новая транзитивная версия требовала Node 22.22. SDK размещается на том же origin, что и сайт; его фактический URL задаётся в `window.PIXELPLUS_AUDIT_CONFIG.ultravoxSdkUrl` вместе с `apiBaseUrl` и публичным `turnstileSiteKey`. Секреты в публичную конфигурацию не входят.

## Контракт HTTP для второго агента

Создание: `POST /api/session`, JSON `{operation_id, channel, turnstile_token}`. `channel` — `chat` или `voice`. Для создания `operation_id` — base64url без padding из 32 случайных байтов; браузер сохраняет его до ответа. Ответ 201: `{session, management_token, report_token}`. Браузер сохраняет оба токена раздельно. Повтор уже принятого создания возвращает 409 `creation_already_accepted` и не создаёт вторую сессию. При потере первого ответа исходные случайные токены не восстанавливаются из хешей; это явно ограниченный случай восстановления.

Управление: `Authorization: Bearer <management_token>`. Все изменяющие запросы существующей сессии содержат:

```json
{
  "session_id": "идентификатор из ответа создания",
  "operation_id": "устойчивый ключ операции",
  "expected_revision": 0,
  "channel_revision": 0,
  "library_version": "версия из ответа создания"
}
```

Это поля приложения. Они не являются параметрами API Ultravox.

Успешный JSON сохраняет поля верхнего уровня для существующего клиента и добавляет `{ok: true, data: <те же публичные поля>}`. При создании `session_token` — совместимый alias `management_token`. Сервер не возвращает хеши токенов, внутренние записи D1, содержимое заключения или зашифрованный join URL.

`GET /api/session/:id` возвращает `session` с идентификаторами, версией, ревизиями, состоянием, таймером, текущим вопросом, сообщениями, состояниями звонка/отчёта и доступными действиями. Варианты содержат `id`, `text` и alias `label`. Вопрос `context_priority` допускает несколько вариантов. Содержания заключения в ответе нет. Истёкший management token даёт 401 `session_expired`; отдельный report token позволяет читать только состояние отчёта, без истории и права изменения.

`POST /api/session/channel`: дополнительно `action: "pause" | "resume" | "switch"`; для `switch` — `channel`. Есть отдельные маршруты `/api/session/pause` и `/api/session/resume`. Смена голосового канала требует подтверждённого окончания предыдущего звонка; пока оно не получено, возвращается 409. Запрос провайдеру и Cron проверяют остановку. Доказанная единственная ревизия остановки может быть принята без ложного конфликта, посторонние изменения требуют обновить состояние.

`POST /api/audit/finish`: дополнительно `reason: "sufficient" | "visitor_request" | "declined" | "time_limit"`, при необходимости `through_event_id` — серверное подтверждение доставки. `recovery_expired` определяет только сервер. Клиент обычно сначала доставляет последние кандидаты через `/api/voice/answers`, затем завершает с новой ревизией. Последний голосовой пакет в самом finish допускается только с принадлежащим сессии `call_id` и проходит тот же нормализатор. Клиентские `AuditAnswer`, методы, ID свидетельств и флаг `explicit` напрямую не принимаются. Сохранение нормализованного последнего пакета и завершение атомарны. При `clarification_required` пакет также сохраняется, а повтор воспроизводит результат. После принятия произнести предусмотренную архитектурой благодарность один раз.

`POST /api/report/generate` возвращает состояние уже существующего задания и инициирует его допустимое продолжение. `GET /api/report/:token` использует отдельный `report_token`: 202 — ожидание, 200 — PDF, 410 — срок истёк. Пропуск KV не создаёт новый рендер.

`POST /api/email/send`: дополнительно `{email, consent: {accepted: true, version: "версия текста согласия"}}`. Согласие сохраняется с серверным временем; отправка разрешена для готового отчёта. При неопределённом результате SMTP автоматического повторного письма нет.

Ошибки: `{ok: false, error: {code, message, retryable, retry_after_seconds}, request_id}`. При 409 клиент перечитывает актуальное состояние; повтор доставки сохраняет исходные тело и `operation_id`. Изменение тела под тем же ключом запрещено. При 429/503 учитывается `Retry-After`.

## Подключение каналов

`src/integration.ts` подключает готовые `chat`, `voiceStart`, `voiceTranscript`, `voiceAnswers`, `ultravoxWebhook`, `reconcile`, `pollVoice` и `recoverVoice`. Мосты ядра — `channel-runtime.ts`, `channel-voice.ts`, `channel-recovery.ts`. Обработчик получает `request` и `{core, env, execution, session?, body?}`, возвращает JSON либо Response. Точка входа ограничивает тело, проверяет токен/версию, Origin и Turnstile перед новым голосовым стартом. Вебхук проверяет подпись исходных байтов. Необязательный справочный `search` остаётся выключен до утверждения разрешённых областей FAQ.

`CoreServices.accept(request, body, event, answers)` валидирует кандидаты и записывает их атомарно. Не передавать клиентское состояние как готовый `AuditState`. `core.reserve(kind, amount, operationId)` резервирует бюджет до внешнего вызова; после вызова — `core.store.settleUsage(reservation.id, actual, now)`, при неизвестном исходе `actual: null`.

`core.humor(request, body, intent)` принимает результат серверной классификации и атомарно сохраняет выбор. `core.acknowledgeHumor(request, body, selectionOperation)` отдельно подтверждает выдачу. Клиент исключает повторное отображение/произнесение по ключу операции. Шутки и служебные события не создают диагностические ответы.

`core.store` предоставляет операции голосовых слотов/звонков, поздних свидетельств и согласования. Их точные сигнатуры — в `src/storage/d1-store.ts`. Восстановление разбирает только пропущенные сохранённые реплики закреплённой библиотеки. Результаты классификации кешируются по звонку и границе исходных событий; повтор после проигрыша CAS не оплачивает тот же разбор. Неизвестный исход внешнего запроса не разрешает повторный расход. Без подтверждённой полноты в PDF сохраняется ограничение.

Голосовой `confirmation_candidate` сам по себе не подтверждает факт. По сохранённым соседним репликам проверяются дословные строки, перечни, числа и диапазоны с явно названными единицами и периодом. Ответ «да/нет» требует точного закреплённого вопроса; составные значения и история работ — явной связи поля со значением. Реплика пользователя «Исправляю:» с дословным пересказом и подтверждением заменяет только единственный подходящий актуальный ответ, сохраняя предыдущий; неоднозначность остаётся спорной. Перефразировки, неназванные единицы и неоднозначные связи не подтверждаются автоматически. Редкий `offTopicReply` проверяет реальное сохранённое сообщение серверным классификатором; клиентская категория шутки не является полномочием. Обычный голосовой пакет не вызывает DeepSeek. После остановки подробная история согласуется отдельно.

Инфраструктуру можно опубликовать до утверждения содержания, сохранив `ALLOW_DRAFT_LIBRARY=false` и `BUDGETS_JSON={}`. Для закрытого режима обязательны реальная D1 со всеми миграциями и `IP_HASH_SALT`: HTTP-ограничитель обращается к ним до проверки библиотеки. KV подключается согласно конфигурации. Ключи внешних провайдеров для проверки закрытого режима не нужны. Cron на пустой D1 не вызывает внешние сервисы.

После настройки ресурсов выполняются `wrangler d1 migrations apply DB --remote` и `wrangler deploy` установленным в `worker` Wrangler. Секреты передаются через `wrangler secret bulk`, без сохранения в публичной конфигурации. Адрес опубликованного Worker необходимо записать в `PUBLIC_WORKER_URL`. Проверка именно закрытого развёртывания:

```powershell
npm run smoke:deployed -- <HTTPS-origin-Worker> <разрешённый-HTTPS-origin-сайта>
```

Она проверяет CORS, отказ без авторизации, доступ к D1 и `503 library_not_approved`; обновляются только счётчики HTTP. После утверждения библиотеки эта проверка намеренно перестанет проходить: открытый режим требует полной приёмки с настроенными провайдерами.
